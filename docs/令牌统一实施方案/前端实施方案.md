## 1. 背景与结论（前端视角）

### 1.1 一句话方案

BackEndV3 本身持有「自签 token → uid」的映射。用户带着自签 token 请求时，BackEndV3 现场用 Ed25519 签名向 UC 换取一对全新的 UC 令牌，把 access_token 回带给前端（供前端调用 UC 接口），refresh_token 留在服务端。不导出数据、不对账、不改 UC 表结构，前端凭据也无需更换。

### 1.2 前端要理解的核心结论

- **前端同时持有两种令牌，各司其职**（这是本轮方案与上游计划差异最大的一点）：
  - 自签 token：调 BackEndV3 的会话凭据，存 localStorage（key `USER_TOKEN`），**长期有效、不做清理**，并兼作兑换 / 刷新 UC 令牌的凭据；
  - UC access_token：仅供调用 UC 接口，约 2h 有效期，存 localStorage（key `UC_ACCESS_TOKEN`）；
- **前端永远拿不到、也不需要 UC refresh_token**：`arknights-yituliu-web` 是机密客户端，刷新必须带 `client_secret`，浏览器不可能持有，刷新一律由 BackEndV3 服务端代做。
- **登录流程与既有的自签 token 存储逻辑都不需要改**。前端新增的只有两件事：① 应用启动 / 进入业务页时若本地无可用 UC access_token，带自签 token 调 `POST /auth/uc-token/issue` 兑换（F3）；② 调 UC 接口遇令牌失效时带自签 token 调 `/auth/token/refresh` 刷新并重试一次（F4）。

### 1.3 上游计划中被取消的目标

上游计划 `统一令牌改造计划.md` 要求「前端只持 UC 令牌，不再携带自签 token」，**该目标已取消**：自签 token 长期在役，前端不得移除既有存储逻辑（见第 7.2 节禁止项）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| UC | UserCenterV1，OAuth2 授权服务器（本仓库） |
| BackEndV3 | 业务后端（外部仓库） |
| 自签 token | BackEndV3 登录令牌，`AES("{id:X}.X.timestamp")` 自签形态，TTL 90 天，Redis 映射 `loginToken:{token} → uid` |
| 迁移兑换 | BackEndV3 凭 uid 现场向 UC 换取一对全新 UC 令牌的动作。**触发点在前端**（本地无 UC access_token 时主动调用兑换接口），签名与兑换在 BackEndV3 服务端完成，前端不接触 UC refresh_token |
| 双撤 | 登出 / 封禁时必须同时撤销 UC 授权与本地 `loginToken`（由 BackEndV3 执行） |

## 3. 前端职责与边界

| 前端做 | 前端不做 |
|---|---|
| 调 BackEndV3 时继续用自签 token | 不持有、不存储 UC refresh_token |
| 应用启动 / 进入业务页时读 localStorage 的 `UC_ACCESS_TOKEN`，**缺失**才带自签 token 调 `POST /auth/uc-token/issue`，并把响应体中的 `access_token` 写入本地 | 不参与兑换的签名与 UC 调用（兑换全部由 BackEndV3 服务端完成） |
| 调 UC 接口时用 UC access_token | 不用 UC access_token 换新令牌 |
| UC 接口 401 时带自签 token 请求 BackEndV3 刷新 | 不直接调 UC `/oauth2/token`（必然被拒） |
| 登出时清理本地自签 token + `UC_ACCESS_TOKEN` | 不删除既有的自签 token 存储逻辑 |

| # | 事项 | 说明 |
|---|---|---|
| F1 | 登录流程不变 | 仍走 `/direct-session` → UC 登录页 → `/complete-login`；响应中拿到自签 token（同现状）。新登录时 BackEndV3 侧同时接住 UC 令牌（refresh_token 加密落库，见 `./BackEndV3侧实施方案.md` 的 B8） |

## 5. 令牌流转契约

### 5.1 兑换接口响应体契约（BackEndV3 → 前端）

前端带自签 token 调 `POST /auth/uc-token/issue`，BackEndV3 把 UC access_token 放在**响应体**返回，前端将其存起来供调 UC 接口使用；调 BackEndV3 的请求不需要切换凭据。

| 字段 | 说明 |
|---|---|
| `access_token` | UC access_token（前端调 UC 接口用） |
| `expires_in` | 有效期（秒） |
| `token_type` | 固定 `Bearer` |
| `scope` | 可选，scope |

> 响应体**不含 `refresh_token`**（不下发浏览器），也不回带用户资料。

### 5.2 前端必须配合的两个实现点

1. **CORS**：前端与 BackEndV3 跨域时，兑换接口与刷新接口需放行前端 origin。令牌走 JSON 响应体，**不再需要配置 `Access-Control-Expose-Headers`**（响应头方案才需要）。
2. **禁止缓存**：响应携带令牌，必须确保 `Cache-Control: no-store`，中间代理与浏览器缓存不得缓存该响应。

### 5.3 为什么刷新只能由服务端做

- `arknights-yituliu-web` 是机密客户端，UC 的 `OAuthTokenServiceImpl.refreshToken` 要求 `client_secret`，浏览器调 UC `/oauth2/token` 必然被拒。
- 前端只需要一个「让 BackEndV3 认出这是哪条会话」的凭据，直接复用现有自签 token：`loginToken:{token} → uid` 本来就在用，`/auth/token/refresh` 按它反查 uid。
- 因此不新造 `sessionId`，不改表结构、不动 Redis key 布局——自签 token 天然「一设备一条」，多端登录无需前端做任何改动。

## 6. 前端时序

### 6.1 登录

```
前端 ──/direct-session──▶ BackEndV3 ──▶ UC 登录页 ──▶ /complete-login
     ◀── 自签 token（存 localStorage，同现状）
     ◀── UC 令牌由 BackEndV3 接住（refresh_token 服务端加密落库，不下发浏览器）
```

### 6.2 存量用户首次进入（迁移，由前端主动触发）

```
前端：应用启动 / 进入业务页 → 读 localStorage 的 UC_ACCESS_TOKEN
      存在   → 直接使用，不请求兑换
      不存在 → 执行下面的动作（前端唯一新增的触发点）
前端 ──Authorization: Bearer <自签 token>──▶ BackEndV3 POST /auth/uc-token/issue
     ◀── 响应体 { access_token, expires_in, token_type, scope }
前端：把 access_token 写入 localStorage（key：UC_ACCESS_TOKEN）
      —— 调 BackEndV3 仍用自签 token，用户全程无感
```

> 触发点与业务请求解耦：只在「本地无 UC access_token」时多一次显式往返，属一次性 / 偶发动作；兑换失败不阻塞业务，等下次启动或下次进入业务页再重试。

### 6.3 UC access_token 过期

```
前端 ──Bearer <UC access_token>──▶ UC 接口 → 401
前端 ──自签 token──▶ BackEndV3 POST /auth/token/refresh
     ◀── 新 UC access_token
前端：更新本地 UC access_token → 重试原 UC 请求一次；失败则提示需重新登录
```

### 6.4 登出

```
前端 ──▶ BackEndV3 /auth/user/logout
前端：清理本地存储（自签 token + UC access_token）
BackEndV3：删 loginToken + 调 UC /oauth2/revoke（双撤，见 R14）
```

## 7. 注意事项

### 7.1 必须做到

- UC 接口的 401 处理必须走「请求 BackEndV3 刷新 → 重试一次」路径，不要直接跳登录页（`gate_types` / 网络抖动也会产生 401）。
- 刷新与兑换必须做并发去重（F5），避免多标签页 / 并发组件同时发起兑换或刷新。
- 兑换请求失败时不得影响主流程：不阻塞业务请求（自签 token 照常可调 BackEndV3），等下次启动 / 下次进入业务页重试；已持有过期 access_token 时后续调 UC 接口 401，走 6.3 刷新自愈。

### 7.2 禁止项

- **绝不要用 UC access_token 当刷新凭据**：access 过期后令牌会轮换、映射断链；且映射条目随刷新无限增长（5 万用户 × 90 天约 5400 万条），不可接受。
- **不得移除既有的自签 token 存储逻辑**：自签 token 一旦成为刷新凭据就永远不能删——上游计划「自签链路彻底移除 / 前端只持 UC 令牌」的目标不再成立。前端若按旧目标清理本地存储，会导致用户刷新链路断裂。

## 8. 测试与验收（前端相关）

1. 打开新前端（localStorage 无 `UC_ACCESS_TOKEN`）→ 前端自动调 `POST /auth/uc-token/issue` → 拿到 UC access_token 并写入 localStorage；同一时刻的 BackEndV3 业务请求照常成功，用户无感。
2. 已有 `UC_ACCESS_TOKEN` 时再次进入不再调用兑换接口；手动清除本地令牌后再进入会命中 BackEndV3 侧缓存，不产生第二次兑换。
3. 该 access_token 调 UC `/oauth2/userinfo` 成功（验证前端直连 UC 可用）。
4. 跨域场景验证兑换接口的 CORS 放行生效，前端能正常调用并读到响应体中的令牌（不再依赖 `Access-Control-Expose-Headers`）。
5. 等 UC access 过期 → 调 UC 接口 401 → 带自签 token 调 `/auth/token/refresh` 成功。
6. 删除 `loginToken:{token}`（模拟会话被登出）后刷新失败，前端提示重新登录。
7. 多端验证：同一账号两个设备登录，各自的自签 token 都能独立刷新、互不踢下线。
8. UC 侧「我的授权」能看到该 client 的记录，且从 UC 侧撤销后刷新失败。
9. 双撤验证：登出后本地自签 token 与 UC access_token 均已清理，UC 刷新能力失效。
10. 确认自签 token 长期有效：迁移通道下线后自签 token 照常可用（前端不得因「迁移结束」而清理它）。
11. 兑换接口失败（如 UC 不可用）时不影响业务：业务请求正常、用户不掉登录，下次进入重试。

> 完整端到端清单见 `./BackEndV3侧实施方案.md` 第 9.1 节。

## 9. 风险与缓解（前端相关）

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R7 | 前端 token 权限过宽 | 浏览器持有 client 全量 scope | 与上游计划 R5 同一问题：收敛该 client 的 `scopes` |
| R13 | 前端未保存兑换返回的 UC access_token | 前端调 UC 接口持续 401 / 不可用 | 前端在 401 后走 F4 刷新即可自愈，刷新成功后重新写入；BackEndV3 侧兑换缓存兜底，重复触发只命中缓存、不会重复调 UC（UC 侧不会被击穿）；埋点统计「UC 接口 401 率」即可发现 |
| R14 | 登出只撤了一侧 | 用户被撤权后仍可用另一份凭证继续访问 | 双撤为必要步骤（BackEndV3 执行 UC `/oauth2/revoke` + 删本地 `loginToken`）；前端登出时须同步清理本地存储（F6）。纳入验收用例（第 8 节第 9 条） |
| R17 | 多设备场景下其他设备登出导致本机刷新失败 | 调 UC 接口 401 且刷新返回 90009 | 自签 token 不受影响、用户不掉登录，属预期行为；前端需实现「刷新失败 → 删除本地 `UC_ACCESS_TOKEN` → 下次启动 / 下次进入业务页重新调用兑换接口」的自愈路径（见 `./BackEndV3侧实施方案.md` 的 B4 / R17） |
