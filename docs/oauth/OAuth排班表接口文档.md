# OAuth 排班表接口

本文档面向 OAuth 接入方，说明通过 OAuth access_token 读写用户排班表的接口。接口复用用户侧既有服务逻辑；用户身份与 OAuth 客户端均由 access_token 决定，请求参数不能指定或覆盖它们。

本文档与《用户排班表接口文档》为同一份业务的两侧入口，差异见 [1.5](#15-与用户侧的差异)。

## 1. 通用约定

### 1.1 认证

所有接口都需要携带有效的 OAuth access_token：

```http
Authorization: Bearer <access_token>
```

服务端从令牌解析出用户 `uid`、OAuth 客户端 `client_id` 与已授权的 `scope` 并注入请求上下文，接入方不能通过请求参数指定这两个值。

令牌缺失、无效或已过期时响应 `code=80001`。

### 1.2 授权范围

| scope | 可访问接口 |
| --- | --- |
| `config.read` | 查询排班表列表 |
| `config.write` | 保存排班表、删除排班表 |

缺少所需 scope 时响应 `code=80008`，`msg` 形如 `缺少授权范围: config.read`。客户端必须在注册时登记相应 scope，并在授权请求中申请它。

> 该 scope 同时覆盖「应用配置」相关接口：`config.read` 也可读取当前客户端名下的用户配置，`config.write` 也可写入或删除用户配置。详见《OAuth 用户配置接口文档》。

被授予元范围 `all` 的令牌（仅管理员手工写库授予的机密客户端）视为已获得全部范围。

### 1.3 数据约定

- 排班表内容必须是合法 JSON 数组，数组中的每一项必须是 JSON 对象。
- 排班记录内部字段不固定，客户端可按业务自定义，例如 `date`、`time`、`status`。
- `schedule` 序列化后的 UTF-8 内容最大 30 KB。
- 每个用户最多保存 5 个排班表，**该上限只在创建时校验**，更新已有排班表不受限制。
- 创建时省略 `id`，由服务端生成并返回；更新时传入现有 `id`，以 `schedule` 内容**完整覆盖**。
- 查询结果按 `updateTime` 倒序排列。

### 1.4 响应格式与错误返回

成功和业务错误均使用统一 JSON 结构：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 业务状态码，`200` 表示成功 |
| `msg` | string | 结果说明 |
| `data` | object / array / null | 响应数据 |

本接口族**两类错误的 HTTP 状态不同**，调用方必须同时判断 HTTP 状态与响应体 `code`：

| 错误类型 | HTTP 状态 | `code` | 示例 |
| --- | --- | --- | --- |
| 请求内容不合法（格式、体积、数量上限、必填项缺失） | `400` | `10002` | 排班表不是 JSON 数组、超过 30 KB、超过 5 个 |
| 业务失败（令牌无效、缺少 scope、无权、不存在） | `200` | `80001` / `80008` / `20001` / `10001` | 缺少 `config.write`、排班表不存在 |

日期时间字段为 ISO-8601 无时区格式，例如 `2026-09-20T12:00:00`。

### 1.5 与用户侧的差异

| 维度 | 本文档（OAuth 侧） | 用户排班表接口文档 |
| --- | --- | --- |
| 路径前缀 | `/oauth2/schedule` | `/user/schedule` |
| 凭证 | OAuth access_token | 用户会话 token |
| 授权范围 | 读取 `config.read`，写入 `config.write` | 不需要 scope |
| 列表接口入参 | 无参数，用户取自令牌 | 必须传 `username` 且须为本人 |
| 归属判定 | 令牌中的 `uid` | 会话中的 `uid` |

请求体、响应体、数据约定与错误码完全一致。按 ID 公开读取排班表走 `/open/schedule/{id}`（无需任何凭证），见《用户排班表接口文档》第 5 节，OAuth 侧无对应接口。

## 2. 查询排班表列表

```http
GET /oauth2/schedule/list
Authorization: Bearer <access_token>
```

需要 `config.read`。返回当前令牌用户自己的排班表列表，**按 `updateTime` 倒序**。无查询参数。

### 2.1 成功响应

HTTP `200`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": [
    {
      "id": 123456789,
      "schedule": [
        {"date": "2026-09-21", "time": "09:00-18:00", "status": "on_duty"}
      ],
      "createTime": "2026-09-20T12:00:00",
      "updateTime": "2026-09-20T12:00:00"
    }
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | integer | 排班表 ID |
| `schedule` | array | 排班表内容，原样返回保存时的 JSON 数组 |
| `createTime` | string | 创建时间 |
| `updateTime` | string | 最近更新时间 |

没有排班表时 `data` 为 `[]`。

### 2.2 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `200` | `80001` | access token 缺失、无效或已过期 |
| `200` | `80008` | 缺少 `config.read` |
| `200` | `40001` | 服务端内部错误 |

## 3. 保存排班表

```http
POST /oauth2/schedule/save
Content-Type: application/json
Authorization: Bearer <access_token>
```

需要 `config.write`。创建或覆盖更新当前令牌用户自己的排班表。

### 3.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | integer | 否 | 排班表 ID。省略即创建；非空则覆盖更新该排班表 |
| `schedule` | array | 是 | 排班表 JSON 数组，每项必须是 JSON 对象 |

### 3.2 请求示例

创建（省略 `id`）：

```json
{
  "schedule": [
    {"date": "2026-09-21", "time": "09:00-18:00", "status": "on_duty"}
  ]
}
```

更新（传入现有 `id`）：

```json
{
  "id": 123456789,
  "schedule": [
    {"date": "2026-09-22", "time": "09:00-18:00", "status": "on_duty"}
  ]
}
```

### 3.3 保存语义

- 传入 `id` 时按 `id` 定位并要求该排班表属于令牌中的用户，`schedule` 内容**完整替换**原有内容，不做字段级合并。
- 省略 `id` 时创建新排班表，创建前校验该用户的排班表数量不超过 5 个。
- 创建与更新都只作用于令牌用户名下的数据，接入方无法指定目标用户。

### 3.4 成功响应

HTTP `200`，`data` 为排班表 ID（创建时为服务端新生成，更新时为传入的 `id`）：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": 123456789
}
```

### 3.5 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `400` | `10002` | `schedule` 缺失、不是 JSON 数组、存在非对象元素、超过 30 KB，或创建时已达 5 个上限 |
| `200` | `80001` | access token 缺失、无效或已过期 |
| `200` | `80008` | 缺少 `config.write`，或传入的 `id` 不属于当前用户 |
| `200` | `20001` | 令牌对应的用户记录不存在 |
| `200` | `40001` | 服务端内部错误 |

## 4. 删除排班表

```http
POST /oauth2/schedule/delete
Content-Type: application/json
Authorization: Bearer <access_token>
```

需要 `config.write`。

### 4.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | integer | 是 | 要删除的排班表 ID |

```json
{
  "id": 123456789
}
```

### 4.2 成功响应

HTTP `200`，`data` 为 `null`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

### 4.3 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `400` | `10002` | `id` 未携带 |
| `200` | `80001` | access token 缺失、无效或已过期 |
| `200` | `80008` | 缺少 `config.write`，或该排班表不存在、不属于当前用户 |
| `200` | `40001` | 服务端内部错误 |

排班表不存在与不属于当前用户返回同一个 `80008`，服务端不区分、不暴露排班表是否存在。

## 5. 常见错误总览

| `code` | 含义 | 出现场景 |
| --- | --- | --- |
| `80001` | 未登录或登录已失效 | access token 缺失、无效或已过期 |
| `80008` | 无权限操作 | 缺少所需 scope，或排班表不属于当前用户 |
| `10001` | 参数错误 | 仅在公开查询接口出现（排班表不存在） |
| `10002` | 参数校验失败 | 请求字段缺失、格式错误、超过 30 KB 或超过 5 个上限 |
| `20001` | 用户不存在 | 令牌对应的用户记录不存在 |
| `40001` | 系统繁忙，请稍后再试 | 稍后重试并保留请求信息 |

完整错误码见《错误码参考》。
