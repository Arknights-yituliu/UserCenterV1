# 终末地玩家数据接口

本文档面向**已登录的终端用户**，说明如何保存《明日方舟：终末地》的玩家数据。

接口位于用户自助面 `/user/ef-accounts`，只操作当前登录用户自己的数据。用户身份取自会话，**不能通过请求参数指定或覆盖**。

玩家数据以整份 JSON 对象上传，服务端**不拆分字段**，序列化后直接以文本形式落库；同一角色（`roleId` + `serverId`）只保存一份，由全部绑定该角色的用户共享。首次上传某个角色时直接建立绑定，无需预订绑定。

## 1. 通用约定

### 1.1 认证

接口需要携带**用户会话凭证**（登录接口下发的 token），支持两种传法：

```http
Authorization: Bearer <会话token>
```

或

```http
UC-Token: <会话token>
```

凭证缺失、会话记录不存在或已被吊销（含被踢下线）时返回 `code=80001`。

### 1.2 响应格式

成功和业务错误均使用统一 JSON 结构，**应用内失败统一返回 HTTP `200` + 业务码**（含请求参数校验失败与登录鉴权失败），调用方必须始终检查响应体中的 `code`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 业务状态码，`200` 表示成功 |
| `msg` | string | 结果说明 |
| `data` | object / null | 响应数据 |

日期时间字段为 ISO-8601 无时区格式，例如 `2026-10-30T20:00:00`。

## 2. 保存玩家数据

```http
POST /user/ef-accounts/player-data/save
Content-Type: application/json
Authorization: Bearer <会话token>
```

目标角色由请求体中的 `roleId` + `serverId` 定位。**当前用户首次上传某个角色时直接建立绑定关系**。

### 2.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `roleId` | string | 是 | 终末地游戏内角色 UID（`card/detail` 的 `roleId`），不超过 32 位可见 ASCII 字符 |
| `serverId` | string | 否 | 服务器 ID（国服常见 `1`），不超过 16 位可见 ASCII 字符；省略时按空串保存 |
| `playerData` | object | 是 | 玩家数据 JSON 对象，整份原样保存，序列化后不超过 2MB |

`roleId`、`serverId` 只允许可见 ASCII 字符（`0x21`-`0x7E`），避免不可见字符进入唯一键。

### 2.2 请求示例

`playerData` 可放入森空岛 `card/detail` 返回的完整结构（`base`、`chars`、`domain` 等），服务端不解析其内部字段：

```json
{
  "roleId": "123456789",
  "serverId": "1",
  "playerData": {
    "base": {
      "roleId": "123456789",
      "name": "玩家昵称",
      "level": 60,
      "worldLevel": 10,
      "charNum": 80,
      "weaponNum": 60
    },
    "chars": [
      {
        "charId": "char_001",
        "level": 80,
        "evolvePhase": 4,
        "potentialLevel": 3
      }
    ],
    "dungeon": {
      "curStamina": 120,
      "maxStamina": 240
    }
  }
}
```

### 2.3 保存语义

- 同一 `roleId` + `serverId` 已存在数据则**整份覆盖** `playerData` 并刷新保存时间，不存在则新增；不会做字段级合并。
- `playerData` 必须是 JSON **对象**，传入数组、字符串或 `null` 返回 `code=10002`。
- 同一个角色 2 秒内只接受一次保存请求，命中限流返回 `code=30006`，建议等待秒数在 `data.retryAfterSeconds` 中。该名额按 `roleId` + `serverId` 计算，**所有绑定该角色的用户共享**。
- 参数校验通过后才占用限流名额，非法请求不会挤占他人的上传名额。

### 2.4 成功响应

HTTP `200`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "roleId": "123456789",
    "serverId": "1",
    "updateTime": "2026-10-30T20:00:00"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `roleId` | string | 本次保存的角色 UID |
| `serverId` | string | 本次保存的服务器 ID，未传时为 `""` |
| `updateTime` | string | 本次保存时间 |

### 2.5 失败响应

| HTTP 状态 | `code` | 含义 | 处理建议 |
| --- | --- | --- | --- |
| `200` | `80001` | 未登录或登录已失效 | 重新登录 |
| `200` | `10002` | 字段缺失、角色标识格式非法、playerData 非对象或超过 2MB | 修正请求后重试 |
| `200` | `30006` | 该角色上传过于频繁 | 按 `data.retryAfterSeconds` 等待后重试 |
| `200` | `40003` | 限流服务不可用 | 稍后重试 |
| `200` | `40001` | 服务端内部错误 | 稍后重试并保留请求信息 |

限流响应示例：

```json
{
  "code": 30006,
  "msg": "该游戏账号上传过于频繁，请稍后再试",
  "data": {
    "retryAfterSeconds": 2
  }
}
```

## 3. 数据存储说明

- 玩家数据保存在 `ef_player_data` 表，`role_id` + `server_id` 唯一，`player_data` 列为 JSON 文本。
- 角色与用户的绑定关系保存在 `ef_account_binding` 表，一个角色可被多个用户绑定，玩家数据共享一份。
- 服务端只保证 JSON 合法、大小受限与归属正确，**不校验、不转换 `playerData` 内部字段**；字段结构变更由写入方自行维护。
