# 终末地玩家数据接口

本文档面向**已登录的终端用户**，说明如何查询已绑定的终末地角色、读取玩家数据，以及保存《明日方舟：终末地》的玩家数据。

接口位于用户自助面 `/user/ef-accounts`，只操作当前登录用户自己的数据。用户身份取自会话，**不能通过请求参数指定或覆盖**。

玩家数据以整份 JSON 对象上传，服务端**不拆分字段**，序列化后直接以文本形式落库；同一角色（`roleId` + `serverId`）只保存一份，由全部绑定该角色的用户共享。首次上传某个角色时直接建立绑定，无需预订绑定。

## 1. 通用约定

### 1.1 认证

接口需要携带**用户会话凭证**（登录接口下发的 token），支持两种传法：

```http
Authorization: Bearer <会话token>
```

或

```http
UC-Token: <会话token>
```

凭证缺失、会话记录不存在或已被吊销（含被踢下线）时返回 `code=80001`。

### 1.2 响应格式

成功和业务错误均使用统一 JSON 结构，**应用内失败统一返回 HTTP `200` + 业务码**（含请求参数校验失败与登录鉴权失败），调用方必须始终检查响应体中的 `code`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 业务状态码，`200` 表示成功 |
| `msg` | string | 结果说明 |
| `data` | object / null | 响应数据 |

日期时间字段为 ISO-8601 无时区格式，例如 `2026-10-30T20:00:00`。

## 2. 查询已绑定的角色列表

```http
GET /user/ef-accounts
Authorization: Bearer <会话token>
```

返回当前用户已绑定的全部终末地角色，**不含玩家数据正文**，按最近导入时间倒序，前端取首条即可默认展示最新数据。

### 2.1 成功响应

HTTP `200`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": [
    {
      "roleId": "123456789",
      "serverId": "1",
      "serverType": "official",
      "serverName": "官服",
      "nickName": "",
      "createTime": "2026-10-30T19:00:00",
      "updateTime": "2026-10-30T20:00:00"
    },
    {
      "roleId": "123456789",
      "serverId": "",
      "serverType": "",
      "serverName": "",
      "nickName": "管理员",
      "createTime": "2026-10-29T09:00:00",
      "updateTime": "2026-10-29T09:00:00"
    }
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `roleId` | string | 终末地游戏内角色 UID |
| `serverId` | string | 服务器 ID，未传时为 `""`；寻访记录导入的绑定行固定为 `""` |
| `serverType` | string | 服务器类型（客户端保存玩家数据时上报），取值由写入方定义、服务端不校验；未上报时为空串 |
| `serverName` | string | 服务器名称（客户端保存玩家数据时上报），未上报时为空串 |
| `nickName` | string | 玩家昵称（寻访记录导入时写入），未导入时为空串 |
| `createTime` | string / null | 绑定创建时间：首次导入该角色数据时写入 |
| `updateTime` | string | 最近一次导入该角色数据的时间 |

> 三个展示字段按绑定行冗余存放：同一角色若既有玩家数据绑定（`serverId` 非空）又有寻访记录绑定（`serverId` 为 `""`），会是**两条独立条目**，各自保留自己的展示信息——寻访记录行通常只有 `nickName`，玩家数据行通常只有 `serverType` / `serverName`。空串表示「尚未获取」而非「值为空」，前端请按「未知」兜底（如回退显示 `roleId`），或按 `roleId` 合并展示。

没有绑定任何角色时 `data` 为 `[]`。

### 2.2 失败响应

| HTTP 状态 | `code` | 含义 | 处理建议 |
| --- | --- | --- | --- |
| `200` | `80001` | 未登录或登录已失效 | 重新登录 |
| `200` | `40001` | 服务端内部错误 | 稍后重试 |

## 3. 读取玩家数据

不传参数时，默认返回当前用户已绑定角色中最近保存的一份玩家数据：

```http
GET /user/ef-accounts/player-data
Authorization: Bearer <会话token>
```

默认选择按玩家数据的 `updateTime` 倒序，同一时间按 `roleId`、`serverId` 升序；仅导入寻访记录或玩家数据已被清理的角色不参与选择。没有可用玩家数据时返回 `code=10002`。

也可以指定角色读取：

```http
GET /user/ef-accounts/player-data?roleId=123456789&serverId=1
Authorization: Bearer <会话token>
```

角色由 `roleId` + `serverId` 定位，**该角色必须已绑定到当前用户**，否则返回 `code=80008`，不能读取他人角色数据。

### 3.1 请求参数

| 参数 | 位置 | 必填 | 说明 |
| --- | --- | --- | --- |
| `roleId` | query | 否 | 终末地游戏内角色 UID，不超过 32 位可见 ASCII 字符；省略或空串时读取最新玩家数据 |
| `serverId` | query | 否 | 服务器 ID，不超过 16 位可见 ASCII 字符；指定 `roleId` 时省略按空串定位；未指定 `roleId` 时不可单独指定非空 `serverId` |

### 3.2 成功响应

HTTP `200`，响应头 `Cache-Control: private, no-cache`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "roleId": "123456789",
    "serverId": "1",
    "playerData": {
      "base": {
        "roleId": "123456789",
        "name": "玩家昵称",
        "level": 60
      }
    },
    "updateTime": "2026-10-30T20:00:00"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `roleId` | string | 角色 UID |
| `serverId` | string | 实际返回角色的服务器 ID；显式指定角色且省略服务器时为 `""` |
| `playerData` | object | 保存时提交的 JSON 对象，服务端原样返回 |
| `updateTime` | string | 最近一次保存时间 |

绑定关系存在但数据行缺失（异常清理场景）时 `data` 为 `null`，客户端可按空数据处理。

### 3.3 失败响应

| HTTP 状态 | `code` | 含义 | 处理建议 |
| --- | --- | --- | --- |
| `200` | `80001` | 未登录或登录已失效 | 重新登录 |
| `200` | `10002` | 无可用默认玩家数据、角色标识格式非法，或未指定 `roleId` 却单独指定 `serverId` | 先导入玩家数据或修正请求后重试 |
| `200` | `80008` | 该角色未绑定到当前用户 | 先通过保存接口导入该角色 |
| `200` | `40001` | 服务端内部错误或存储数据损坏 | 稍后重试并保留请求信息 |

## 4. 保存玩家数据

```http
POST /user/ef-accounts/player-data/save
Content-Type: application/json
Authorization: Bearer <会话token>
```

目标角色由请求体中的 `roleId` + `serverId` 定位。**当前用户首次上传某个角色时直接建立绑定关系**。

### 4.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `roleId` | string | 是 | 终末地游戏内角色 UID（`card/detail` 的 `roleId`），不超过 32 位可见 ASCII 字符 |
| `serverId` | string | 否 | 服务器 ID（国服常见 `1`），不超过 16 位可见 ASCII 字符；省略时按空串保存 |
| `serverType` | string | 否 | 服务器类型，最长 64 字符；取值由写入方定义，服务端只校验长度 |
| `serverName` | string | 否 | 服务器名称，最长 64 字符 |
| `playerData` | object | 是 | 玩家数据 JSON 对象，整份原样保存，序列化后不超过 2MB |

`roleId`、`serverId` 只允许可见 ASCII 字符（`0x21`-`0x7E`），避免不可见字符进入唯一键。
`serverType` / `serverName` 最长 64 字符，省略或传 `null` 时**沿用绑定关系中的已有值**，显式传空串才会清空；首次建立绑定且未上报时落空串。它们只用于角色列表展示，不参与角色定位与归属校验。

### 4.2 请求示例

`playerData` 可放入森空岛 `card/detail` 返回的完整结构（`base`、`chars`、`domain` 等），服务端不解析其内部字段：

```json
{
  "roleId": "123456789",
  "serverId": "1",
  "serverType": "official",
  "serverName": "官服",
  "playerData": {
    "base": {
      "roleId": "123456789",
      "name": "玩家昵称",
      "level": 60,
      "worldLevel": 10,
      "charNum": 80,
      "weaponNum": 60
    },
    "chars": [
      {
        "charId": "char_001",
        "level": 80,
        "evolvePhase": 4,
        "potentialLevel": 3
      }
    ],
    "dungeon": {
      "curStamina": 120,
      "maxStamina": 240
    }
  }
}
```

### 4.3 保存语义

- 同一 `roleId` + `serverId` 已存在数据则**整份覆盖** `playerData` 并刷新保存时间，不存在则新增；不会做字段级合并。
- `playerData` 必须是 JSON **对象**，传入数组、字符串或 `null` 返回 `code=10002`。
- `serverType` / `serverName` 随绑定关系一起保存，采用**自然回填**：服务端不主动补拉服务器信息，也不提供单独的补数接口。请客户端在每次保存时都尽量带上这两个字段，存量角色会在下一次导入时补齐；长期不导入的角色保持空串。省略或传 `null` 只沿用旧值，不会抹掉已经回填的内容；寻访记录导入不会写入或清空这两列。
- 同一个角色 2 秒内只接受一次保存请求，命中限流返回 `code=30006`，建议等待秒数在 `data.retryAfterSeconds` 中。该名额按 `roleId` + `serverId` 计算，**所有绑定该角色的用户共享**。
- 参数校验通过后才占用限流名额，非法请求不会挤占他人的上传名额。

### 4.4 成功响应

HTTP `200`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "roleId": "123456789",
    "serverId": "1",
    "updateTime": "2026-10-30T20:00:00"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `roleId` | string | 本次保存的角色 UID |
| `serverId` | string | 本次保存的服务器 ID，未传时为 `""` |
| `updateTime` | string | 本次保存时间 |

### 4.5 失败响应

| HTTP 状态 | `code` | 含义 | 处理建议 |
| --- | --- | --- | --- |
| `200` | `80001` | 未登录或登录已失效 | 重新登录 |
| `200` | `10002` | 字段缺失、角色标识格式非法、playerData 非对象或超过 2MB | 修正请求后重试 |
| `200` | `30006` | 该角色上传过于频繁 | 按 `data.retryAfterSeconds` 等待后重试 |
| `200` | `40003` | 限流服务不可用 | 稍后重试 |
| `200` | `40001` | 服务端内部错误 | 稍后重试并保留请求信息 |

限流响应示例：

```json
{
  "code": 30006,
  "msg": "该游戏账号上传过于频繁，请稍后再试",
  "data": {
    "retryAfterSeconds": 2
  }
}
```

## 5. 数据存储说明

- 玩家数据保存在 `ef_player_data` 表，`role_id` + `server_id` 唯一，`player_data` 列为 JSON 文本。
- 角色与用户的绑定关系保存在 `ef_account_binding` 表，一个角色可被多个用户绑定，玩家数据共享一份。
- `ef_account_binding` 冗余 `server_type` / `server_name`（保存玩家数据时上报）与 `nick_name`（寻访记录导入时写入），三者按绑定行存放、只用于角色列表展示，不参与唯一键与归属校验；服务端不校验其取值，只限制长度。
- 服务端只保证 JSON 合法、大小受限与归属正确，**不校验、不转换 `playerData` 内部字段**；字段结构变更由写入方自行维护。
