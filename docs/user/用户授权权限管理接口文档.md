# 用户授权权限管理接口

本文档面向**已登录的终端用户**，说明用户如何查看某个已授权应用当前拥有哪些权限，以及如何为它**追加**或**取消**权限。

与《用户授权应用管理接口文档》（`用户授权应用管理接口文档.md`）的分工：

| 文档 | 管理粒度 | 回答的问题 |
| --- | --- | --- |
| 用户授权应用管理接口 | **应用级** | "我授权了哪些应用" / "整体撤销某个应用" |
| 本文档 | **权限级** | "某应用具体有哪些权限" / "给某应用加/减权限" |

两者同属用户自助面 `/user/**`，都只操作**当前登录用户自己**的数据，可并存使用：先按应用列表找到目标应用，再用本文档的接口调整其权限。

## 1. 通用约定

### 1.1 认证

所有接口都需要携带**用户会话凭证**（登录接口下发的 token），支持两种传法：

```http
Authorization: Bearer <会话token>
```

或

```http
UC-Token: <会话token>
```

服务端从会话中取得用户 `uid`。用户不能通过请求参数指定 uid，接口只作用于当前登录用户名下的授权。

### 1.2 响应格式

成功和业务错误均使用统一 JSON 结构：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 业务状态码，`200` 表示成功 |
| `msg` | string | 结果说明 |
| `data` | object / array / null | 响应数据 |

调用方应始终检查响应体中的 `code`，不能只判断 HTTP 状态码。

### 1.3 权限标识与可选范围

- 权限用**英文标识**表示（如 `user.read`），定义在 `OAuthScope` 枚举中。
- 用户**可勾选的范围 = 系统全部可选权限**，即枚举中所有未被标记为「仅限管理员手工授予」的权限：

| 标识 | 说明 |
| --- | --- |
| `user.read` | 读取你的用户 ID、昵称和头像 |
| `user.profile` | 读取并修改你的个人资料 |
| `config.read` | 读取该应用名下的用户配置，以及查看你的排班表 |
| `config.write` | 创建、修改或删除该应用名下的用户配置，以及保存或删除你的排班表 |
| `gama-data.read` | 读取用户游戏数据 |
| `gama-data.write` | 写入用户游戏数据 |

- **元范围 `all` 不向用户开放**：它不会出现在 `selectableScopes` 中，用户提交也会被拒（`code=90003`）。`all` 属于管理员专属能力，只能由管理员直接写库授予，且仅对机密客户端生效。
- **不受该应用登记范围限制**：用户可以为一个应用追加它**从未登记、也从未申请过**的权限。这是刻意设计——用户对自己数据有完全的支配权，不因接入方"没申请"而受限。

## 2. 查看我对某应用的授权权限

```http
GET /user/oauth/grants/scopes?client_id=client-a
Authorization: Bearer <会话token>
```

### 2.1 查询参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `client_id` | string | 是 | 应用（OAuth 客户端）ID |

参数名是下划线形式 `client_id`（历史原因），与请求体里的驼峰 `clientId` 不同，请勿混用。

### 2.2 返回字段

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "clientId": "client-a",
    "clientName": "我的博客站",
    "grantedScopes": [
      { "code": "user.read", "desc": "读取你的用户 ID、昵称和头像" },
      { "code": "user.profile", "desc": "读取并修改你的个人资料" }
    ],
    "selectableScopes": [
      { "code": "user.read", "desc": "读取你的用户 ID、昵称和头像" },
      { "code": "user.profile", "desc": "读取并修改你的个人资料" },
      { "code": "config.read", "desc": "读取该应用名下的用户配置，以及查看你的排班表" },
      { "code": "config.write", "desc": "创建、修改或删除该应用名下的用户配置，以及保存或删除你的排班表" },
      { "code": "gama-data.read", "desc": "读取用户游戏数据" },
      { "code": "gama-data.write", "desc": "写入用户游戏数据" }
    ]
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `clientId` | string | 应用（OAuth 客户端）ID |
| `clientName` | string | 应用中文名称（来自应用注册信息） |
| `grantedScopes` | array | 当前已授予该应用的权限，即勾选基线 |
| `selectableScopes` | array | 系统全部可选权限，即勾选全集（不含 `all`） |

数组元素字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | 权限标识 |
| `desc` | string | 权限中文描述；若标识不在枚举中（历史遗留），原样返回该标识，保证界面不出现空白项 |

### 2.3 `grantedScopes` 的口径

| 场景 | `grantedScopes` |
| --- | --- |
| 用户曾通过本文档接口或授权确认页调整过该应用的权限 | 用户自定义的那份权限集合 |
| 用户**从未**自定义过 | 该应用的**登记范围** |

未自定义时回退到登记范围，是作为**勾选基线**使用：用户首次进入管理页时，原有权限默认处于勾选态，避免用户只想"减一项"却因为基线为空而意外丢掉其他权限。

### 2.4 与其他接口的差异

授权确认页（`GET /oauth2/consent/info`）返回的 `grantedScopes` **未自定义时为空数组**，由前端回退到本次申请范围。两处口径不同是刻意设计，前端按各自默认值初始化即可。

## 3. 为某应用追加授权权限

```http
POST /user/oauth/grants/scopes/grant
Content-Type: application/json
Authorization: Bearer <会话token>
```

请求体：

```json
{
  "clientId": "client-a",
  "scopes": ["user.profile", "gama-data.read"]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `clientId` | string | 是 | 应用（OAuth 客户端）ID，1-128 个字符 |
| `scopes` | array\<string\> | 是 | 本次要追加的权限标识，不能为空数组；元素须为系统可选权限 |

响应：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

### 3.1 追加语义（只增不减）

1. 计算基线：取**第 2 节**的 `grantedScopes`（未自定义过时为应用登记范围）。
2. 与请求的 `scopes` 取**并集**，作为该用户对该应用的**新授权范围**。
3. 覆盖写入用户自定义授权范围表（唯一键 `uid + clientId`，`ON DUPLICATE KEY UPDATE` 原子 upsert，并发提交不会产生重复行）。
4. **立即生效**：同步改写该用户在该应用下已签发的 `access_token` 与 `refresh_token` 的 `scope`（保留各自剩余有效期，不延长授权），并同步授权台账，使"我的授权"列表展示调整后的范围。
5. **下次授权自动延续**：此后该用户对该应用发起的每次授权都按这份范围签发，不再受客户端本次申请范围约束。

### 3.2 幂等与越权

- 操作**幂等**：重复追加同一权限不会报错，结果一致（并集）。
- 只能操作**自己名下**的授权；服务端忽略任何与他人 uid 相关的目标。
- 追加**不会**收窄已有权限：只提交新增项即可，原有权限自动保留。

### 3.3 示例

应用 `client-a` 当前已授予 `user.read`，追加 `user.profile`：

```json
{ "clientId": "client-a", "scopes": ["user.profile"] }
```

调用后再查**第 2 节**接口，`grantedScopes` 变为 `user.read` + `user.profile`。

## 4. 取消某应用的已授权权限

```http
POST /user/oauth/grants/scopes/revoke
Content-Type: application/json
Authorization: Bearer <会话token>
```

请求体：

```json
{
  "clientId": "client-a",
  "scopes": ["gama-data.read"]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `clientId` | string | 是 | 应用（OAuth 客户端）ID，1-128 个字符 |
| `scopes` | array\<string\> | 是 | 本次要取消的权限标识，不能为空数组 |

响应：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

### 4.1 取消语义（只减不增）

1. 计算基线：同 **3.1 节**的 `grantedScopes`。
2. 与请求的 `scopes` 取**差集**（基线中移除请求项），作为新的授权范围。
3. 校验**剩余权限不可为空**：若移除后为空，说明该应用已无任何权限，令牌失去意义，此时返回 `code=10001`，提示改用整体撤销授权。
4. 写入与生效方式同追加：覆盖写入自定义范围表，并同步已签发令牌与台账。

### 4.2 幂等与越权

- 操作**幂等**：取消一项**未被授予**的权限不会报错，会被忽略（差集结果不变），可直接用于"按钮多次点击 / 重试"。
- 只能操作**自己名下**的授权。
- 取消**不会**影响其他应用：同步令牌时只改写 `clientId` 匹配的令牌记录。

### 4.3 示例

应用 `client-a` 当前已授予 `user.read` + `user.profile`，取消 `user.profile`：

```json
{ "clientId": "client-a", "scopes": ["user.profile"] }
```

调用后 `grantedScopes` 只剩 `user.read`；该应用已签发的令牌立即失去 `user.profile` 能力。

## 5. 权限调整对已签发令牌的影响

追加与取消都是**立即生效**的，不需要用户重新授权，也不需要等令牌过期：

- 服务端通过反向索引 `uc:uid:oauth:{uid}` 定位该用户全部令牌，逐个比对记录中的 `clientId`，只改写归属目标应用的 `access_token` 与 `refresh_token` 的 `scope` 字段。
- 回写时**沿用各自的剩余有效期**，不因权限调整而延长授权时长。
- 索引中已过期或已吊销的令牌会被顺手清理，并跳过不处理。

因此调整权限后，接入方**下一次调用**受影响接口时就会按新范围被校验，无需等待令牌刷新。

## 6. 错误码

| HTTP | code | 说明 |
| --- | --- | --- |
| 200 | 200 | 操作成功 |
| 400 | 10002 | 参数校验失败：`clientId` 为空或超长、`scopes` 为空数组 |
| 200 | 10001 | `scopes` 归一化后为空（全是空白项）；取消后剩余权限为空 |
| 200 | 90001 | 应用不存在或已停用 |
| 200 | 90013 | 应用待管理员审批或已被封禁 |
| 200 | 90003 | 提交了系统不支持的权限标识（含元范围 `all`） |
| 200 | 80001 | 未登录或登录已失效（未携带会话凭证） |
| 200 | 40001 | 缺少 `client_id` 查询参数，或发生未处理的服务端异常 |

当前实现中，业务异常由统一异常处理器返回 HTTP `200`；只有请求体参数校验失败返回 HTTP `400`。调用方应以响应体中的 `code` 为准。

## 7. 与相邻接口的关系

- **与整体撤销**（`POST /user/oauth/grants/revoke`）：本文档的取消是**权限级**的、可反复微调；要彻底收回应用（含全部权限、全部历史授权记录）应使用整体撤销。取消到空会被拒绝，正是为了引导用户走整体撤销，避免留下"有令牌但无权限"的悬空状态。
- **与授权确认页**（`POST /oauth2/consent`，字段 `scopes`）：确认页提交的 `scopes` 是一次**覆盖式**设置（以提交集合为准），与本文档共用同一张用户自定义授权范围表，因此两侧的调整会互相延续——在确认页取消的权限，管理页也看不到；在管理页追加的权限，下次登录确认页会默认勾选。
- **与 OAuth 协议端点**：接入方按协议主动吊销令牌应使用 `POST /oauth2/revoke`；本文档是用户自助视角，两者不同视角、互不冲突，最终都作用于同一份授权状态。
