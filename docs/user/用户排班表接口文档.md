# 用户排班表接口

本文档面向**已登录的终端用户**，说明用户如何保存、查询和删除自己名下的排班表。

接口位于用户自助面 `/user/schedule`，只操作当前登录用户自己的数据；排班表归属按会话中的 `uid` 校验，用户不能通过请求参数指定或覆盖。第 5 节另有**无需登录的公开查询接口** `/open/schedule/{id}`。

本文档与《OAuth 排班表接口文档》为同一份业务的两侧入口，差异见 [1.4](#14-与-oauth-版的差异)。

## 1. 通用约定

### 1.1 认证

`/user/schedule/**` 需要携带**用户会话凭证**（登录接口下发的 token），支持两种传法：

```http
Authorization: Bearer <会话token>
```

或

```http
UC-Token: <会话token>
```

服务端从会话中取得用户 `uid`。凭证缺失、会话记录不存在或已被吊销（含被踢下线）时返回 `code=80001`——会话状态实时读取，因此"踢下线"立即生效。

`GET /open/schedule/{id}` **无需任何凭证**。

### 1.2 数据约定

- 排班表内容必须是合法 JSON 数组，数组中的每一项必须是 JSON 对象。
- 排班记录内部字段不固定，客户端可按业务自定义，例如 `date`、`time`、`status`。
- `schedule` 序列化后的 UTF-8 内容最大 30 KB。
- 每个用户最多保存 5 个排班表，**该上限只在创建时校验**，更新已有排班表不受限制。
- 创建时省略 `id`，由服务端生成并返回；更新时传入现有 `id`，以 `schedule` 内容**完整覆盖**。
- 查询结果按 `updateTime` 倒序排列。

### 1.3 响应格式与错误返回

成功和业务错误均使用统一 JSON 结构：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | integer | 业务状态码，`200` 表示成功 |
| `msg` | string | 结果说明 |
| `data` | object / array / null | 响应数据 |

本接口族**两类错误的 HTTP 状态不同**，调用方必须同时判断 HTTP 状态与响应体 `code`：

| 错误类型 | HTTP 状态 | `code` | 示例 |
| --- | --- | --- | --- |
| 请求内容不合法（格式、体积、数量上限、必填项缺失） | `400` | `10002` | 排班表不是 JSON 数组、超过 30 KB、超过 5 个 |
| 业务失败（未登录、无权、不存在） | `200` | `80001` / `80008` / `20001` / `10001` | 无权更新他人排班表、排班表不存在 |

日期时间字段为 ISO-8601 无时区格式，例如 `2026-09-20T12:00:00`。

### 1.4 与 OAuth 版的差异

| 维度 | 本文档（用户侧） | OAuth 排班表接口文档 |
| --- | --- | --- |
| 路径前缀 | `/user/schedule` | `/oauth2/schedule` |
| 凭证 | 用户会话 token | OAuth access_token |
| 授权范围 | 不需要 scope | 读取 `config.read`，写入 `config.write` |
| 列表接口入参 | 必须传 `username` 且须为本人 | 无参数，用户取自令牌 |
| 公开按 ID 查询 | `/open/schedule/{id}`，无需登录 | 同左（无 OAuth 版本） |

请求体、响应体、数据约定与错误码完全一致。

## 2. 保存排班表

```http
POST /user/schedule/save
Content-Type: application/json
Authorization: Bearer <会话token>
```

创建或覆盖更新当前用户自己的排班表。

### 2.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | integer | 否 | 排班表 ID。省略即创建；非空则覆盖更新该排班表 |
| `schedule` | array | 是 | 排班表 JSON 数组，每项必须是 JSON 对象 |

### 2.2 请求示例

创建（省略 `id`）：

```json
{
  "schedule": [
    {"date": "2026-09-21", "time": "09:00-18:00", "status": "on_duty"}
  ]
}
```

更新（传入现有 `id`）：

```json
{
  "id": 123456789,
  "schedule": [
    {"date": "2026-09-22", "time": "09:00-18:00", "status": "on_duty"}
  ]
}
```

### 2.3 保存语义

- 传入 `id` 时按 `id` 定位并要求该排班表属于当前用户，`schedule` 内容**完整替换**原有内容，不做字段级合并。
- 省略 `id` 时创建新排班表，创建前校验当前用户的排班表数量不超过 5 个。
- 创建与更新都只作用于当前用户名下的数据。

### 2.4 成功响应

HTTP `200`，`data` 为排班表 ID（创建时为服务端新生成，更新时为传入的 `id`）：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": 123456789
}
```

### 2.5 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `400` | `10002` | `schedule` 缺失、不是 JSON 数组、存在非对象元素、超过 30 KB，或创建时已达 5 个上限 |
| `200` | `80001` | 未登录或登录已失效 |
| `200` | `80008` | 传入的 `id` 不属于当前用户 |
| `200` | `20001` | 当前用户记录不存在 |
| `200` | `40001` | 服务端内部错误 |

## 3. 查询自己的排班表列表

```http
GET /user/schedule/list?username={username}
Authorization: Bearer <会话token>
```

返回当前用户自己的排班表列表，**按 `updateTime` 倒序**。

### 3.1 查询参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `username` | string | 是 | 用户名，必须属于当前登录用户 |

`username` 只用于身份二次确认：传入他人的用户名会返回 `80008`，不会返回他人的数据。

### 3.2 成功响应

HTTP `200`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": [
    {
      "id": 123456789,
      "schedule": [
        {"date": "2026-09-21", "time": "09:00-18:00", "status": "on_duty"}
      ],
      "createTime": "2026-09-20T12:00:00",
      "updateTime": "2026-09-20T12:00:00"
    }
  ]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | integer | 排班表 ID |
| `schedule` | array | 排班表内容，原样返回保存时的 JSON 数组 |
| `createTime` | string | 创建时间 |
| `updateTime` | string | 最近更新时间 |

没有排班表时 `data` 为 `[]`。

### 3.3 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `400` | `10002` | `username` 未携带或为空 |
| `200` | `80001` | 未登录或登录已失效 |
| `200` | `80008` | `username` 不属于当前用户 |
| `200` | `20001` | `username` 对应的用户不存在 |
| `200` | `40001` | 服务端内部错误 |

## 4. 删除排班表

```http
POST /user/schedule/delete
Content-Type: application/json
Authorization: Bearer <会话token>
```

### 4.1 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | integer | 是 | 要删除的排班表 ID |

```json
{
  "id": 123456789
}
```

### 4.2 成功响应

HTTP `200`，`data` 为 `null`：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": null
}
```

### 4.3 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `400` | `10002` | `id` 未携带 |
| `200` | `80001` | 未登录或登录已失效 |
| `200` | `80008` | 该排班表不存在或不属于当前用户 |
| `200` | `40001` | 服务端内部错误 |

排班表不存在与不属于当前用户返回同一个 `80008`，服务端不区分、不暴露排班表是否存在。

## 5. 按 ID 公开查询排班表

```http
GET /open/schedule/{id}
```

**无需任何凭证**，按 ID 返回完整排班表对象，结构与 [3.2](#32-成功响应) 中的单个对象相同。

拿到排班表 ID 的任何一方都可以读取其完整内容，请勿将 ID 视为保密凭据。

### 5.1 失败响应

| HTTP 状态 | `code` | 含义 |
| --- | --- | --- |
| `200` | `10001` | 排班表不存在 |
| `200` | `40001` | 服务端内部错误 |

## 6. 常见错误总览

| `code` | 含义 | 出现场景 |
| --- | --- | --- |
| `80001` | 未登录或登录已失效 | 会话凭证缺失、无效或已过期 |
| `80008` | 无权限操作 | 排班表不属于当前用户、`username` 非本人、`id` 不存在 |
| `10001` | 参数错误 | 公开查询的排班表不存在 |
| `10002` | 参数校验失败 | 请求字段缺失、格式错误、超过 30 KB 或超过 5 个上限 |
| `20001` | 用户不存在 | 当前用户记录或查询的 `username` 不存在 |
| `40001` | 系统繁忙，请稍后再试 | 稍后重试并保留请求信息 |

完整错误码见《错误码参考》。
